# GTLSUPBJAVA 执行规则

本文件是 **GTLSUPBJAVA（GTLsupb 模组）** 项目的唯一规则来源。工程根：`E:\GTL\GTLSUPBJAVA`，准则库：`E:\GTL\API准则代码库`。

**开始任何任务前，完整读取 `AGENTS.md`、`执行规则.md`、`启动上下文.md`。** 禁止日常递归读取全部 Markdown，禁止从头读取 `工作日志.md`。

规则编号全局唯一、只增不改。新增规则追加到本文件末尾并顺延编号；每次任务开始重读本文件时新规则自动生效。

**关于来源**：本文件的规则由「本模组开发中已发生的真实故障」反推得到，只保留可复用的过程纪律，不携带其他工程的版本号、依赖、API、命名空间或代码。

## 一、基础规则（底层逻辑，不可变更）

### 规则 1：任务前读精简上下文，任务后同步上下文与日志

每次任务开始前，只完整读取 `AGENTS.md`、`执行规则.md`、`启动上下文.md`。需要其他资料时只读相关文件的相关段落。任务结束后必须把需求、结论、改动、关键决策、验证结果、遗留风险与踩坑追加到 `工作日志.md`，并把当前有效状态同步到 `启动上下文.md`。

### 规则 2：模型或会话切换后首个动作固定读启动文件

不管换了什么模型、什么会话、什么智能体环境，第一个项目动作永远是完整读取 `AGENTS.md`、`执行规则.md`、`启动上下文.md`。未完成前不得执行其他项目动作。

### 规则 3：禁止使用不确定字眼

不允许使用「可能」「也许」「大概」「应该是」等不确定性字眼。信息不足无法确定，就说「不知道」；做不到，就说「不会」。必须给出确定的判断，并说明依据（文件、命令输出、字节码、日志）。

### 规则 4：用户确定的功能不可擅自更改

用户已经确定的功能不允许擅自修改。唯二例外：

- 在 MC 1.20.1 Forge 环境下可行性极低、根本无法实现；
- 会导致致命冲突或崩溃。

命中例外时必须先暂停任务、说明原因、给出替代方案让用户选择，不得默默改动。

### 规则 5：任务前必须审查合理性与明确性

接到任务时先审查：任务在当前上下文是否合理；提示词是否无歧义；是否存在多种实现方向；任务的边界与预期结果是什么。任一不明确，先暂停提问，明确后再动手。

审查结论必须写明「我打算做什么、不做什么、验收标准是什么」。

### 规则 6：规则由底向上同步

本章规则是底层逻辑。后续新增规则**物理上一律追加到本文件末尾并按全局顺序顺延编号**。若新规则的内容属本章范围，必须在规则正文首行标注「本规则属基础规则组，与规则 1~9 同等约束力」。子智能体同样受全部规则约束。

### 规则 7：改动必须可验证，禁止假成功

任何改动都要给出验证方式并真的执行：

- Java 产物：构建必须退出码 0，产物存在，且解包核对（见规则 14）；
- 语言文件：`zh_cn.json` 与 `en_us.json` 键集必须一致，缺键视为未完成；
- 配置文件：必须能被 Toma's configuration 解析；
- 无法在当前环境验证的部分（如进游戏行为），必须明确标注「待游戏内验证」，不得当作已完成。

**构建失败绝不报告成功。** 退出码 0 不等于成功。

### 规则 8：不破坏可用状态，先备份后覆盖

在替换任何「当前能正常运行」的文件前，先保留原件（另存 / 改名 / 新目录），确保随时可回退。禁止用未经编译验证的代码直接覆盖唯一可用副本。

备份命名约定：`<工程根>\..\旧版备份-YYYYMMDD\`（同日多次用 `-YYYYMMDD-HHmmss`）。

### 规则 9：禁止照搬其他工程

`C:\IDEA\GTL-Enhancedcore`、GTLUltimate、GTPcore 等均为**只读参考**，仅允许查阅其记录的「踩过的坑」与「发现的问题」。

- 禁止复制其任何版本号、依赖清单、构建脚本、API 用法、命名空间、机器清单、代码。
- 它们基于的 gtlcore / GTCEu 版本与本项目不同（本项目 GTCEu 1.4.4），版本与依赖结构均不适用。
- 任何从其他工程获得的 API 结论，未在本项目 `参考/` 源码或本机反编译产物中核实前，禁止写入本项目代码。

## 二、项目执行规则（操作层）

### 规则 10：命名空间与注册 ID 一经发布永不更改

一旦产生 Java 产物，其命名空间、注册 ID、Java 包名即绑定世界存档、方块状态、语言键与模型路径。

- 发布后禁止改名、禁止更换注册位置、禁止删除。
- 项目「改名」只允许改显示名、产物文件名、文件夹名。
- 在构建出第一个可分发产物之前，命名空间为**预留状态**，可在 `启动上下文.md` 中修改；一旦冻结即不可更改。

### 规则 11：颜色与文本走翻译键，文案一律中文

固定可见文字一律进语言文件（`src/main/resources/assets/gtlsupb/lang/zh_cn.json` / `en_us.json`）。代码内禁止拼接 `§` 颜色码；需要着色时使用组件样式 API，把颜色交给参数。`§` 只允许出现在语言文件的值里或专用彩虹水印工具函数内。

新增机器 / 物品 / 界面文案必须**同时**提供 `zh_cn` 与 `en_us` 两份，缺一即视为未完成。**面向玩家的默认语言是中文**。

配置文件的注释（`@Configurable.Comment`）为静态文本不走语言键，必须在代码内直接中英双语、中文在前。

### 规则 12：网络包编解码必须读写配对，注册顺序只追加

新增 / 修改网络包时，`encode` 与 `decode` 的读写类型与顺序必须一一配对（`writeVarInt`↔`readVarInt`、`writeLong`↔`readLong`、`writeBoolean`↔`readBoolean` 等）。混用不会报错，只会静默错乱（真实故障：按钮点了没反应、列表恒空）。

网络通道的消息注册顺序绑定协议 ID，一经发布不得重排；新增消息只能追加到末尾，并同步提升 `PROTOCOL_VERSION`。

### 规则 13：排查第三方 API 行为必须先源码或字节码实证

怀疑任何模组（gtlcore / GTCEu / AE2 / FTB / JEI / Jade 等）的行为或 API 语义时，必须先读 `参考/` 下的官方源码，或用 `javap` 读字节码实证，再下结论。禁止凭经验猜测。

实证结论必须写入 `API标准.md`，未记录视为未完成。

### 规则 14：构建验证必须解包产物实证，禁止只看脚本输出

构建退出码 0 不代表产物正确（真实故障：构建实际失败时脚本误报成功，部署的是旧产物）。构建后必须：

- 解包产物核对本次改动的关键内容（新增 / 修改的类、资源、语言键、字节码引用），确认不是旧产物；
- 比对构建产物与部署位置的哈希（SHA-256）一致；
- 确认部署目录无同 ID 旧产物残留。

### 规则 15：Mixin 使用准入与规范

Mixin / 访问转换器是**最后手段**，不是工具。使用前必须先穷尽替代方案并在 `功能与需求.md` 记录，用户确认后才可实施。替代方案检查顺序：

事件系统 → 子类覆写 → 模组自带钩子（配方修饰器、行为回调）→ 数据层 → 能力包装。

用户确认后实施规范：

- 优先 `@Inject`，其次 `@ModifyArg` / `@ModifyExpressionValue`，`@Redirect` 再次，`@Overwrite` 最后且必须写明理由；
- `@Shadow` 字段禁止带初始化器、禁止声明 `final`；`@Shadow` 只解析目标类自身字段，父类字段必须改用 `@Accessor`；
- `@Accessor` 接口与 `@Mixin` 类同样必须注册进 mixin 配置（`src/main/resources/gtlsupb.mixin.json`），漏注册会在启动期崩溃；
- 辅助类禁止放在 mixin 配置的包内，否则运行期报「不能直接引用」并崩溃；
- 新增 mixin 必须同步注册进配置并确认 remap 设置正确（第三方模组类默认需要 `remap = false`；原版重写方法在运行期是 SRG 名，按官方名注入会失败）。

### 规则 16：排查卡顿 / 崩溃必须先读运行日志

排查进服卡顿、崩溃、异常时，第一步必须读取游戏实例的 `logs/`（`latest.log`、`debug.log`、`crash-reports/`）用实际日志定位，禁止仅凭代码静态猜测。

- 崩溃类问题先看崩溃报告与日志中的 `Mixin apply failed`、`NoSuchMethodError`、`Caused by`、`Suspected Mods`，再用 `javap` 核对可疑类；
- 结论必须写入 `工作日志.md` 并注明依据（日志文件、时间段、关键行）。

### 规则 17：gtlcore 编译期与运行期版本核对

本项目编译期依赖 `libs/gtlcore-1.2.2.8-fix6.jar`，运行期由实例提供 gtlcore（当前为 **1.2.3.2**）。两版本之间方法签名可能变化，**真实故障**：`OverlimitStockingPatternBufferPartMachine.getMERecipeHandlerTraits()` 按 1.2.2.8 编译、运行期在 1.2.3.2 上抛 `NoSuchMethodError`。

因此：

- 覆写 / 实现 gtlcore 类的方法前，必须用 `参考/GTLCore-version-1.2.3.2-fix1`（运行期源码）核对方法签名；
- 方法签名在编译期依赖与运行期依赖之间不一致时，优先删除覆写让基类提供，或与运行期签名对齐；
- 新增对 gtlcore 类的依赖必须同时核对两个版本的签名，并在 `API标准.md` 记录差异。

### 规则 18：构建命令规范

构建必须使用统一命令一次完成：

1. **先终止守护进程与 Java 进程**：`.\gradlew.bat --stop`，必要时结束残留 `java` 进程（避免 Loom 缓存损坏）。
2. **统一命令**：`$env:JAVA_HOME='...\.jdks\temurin-17'` 后执行 `.\gradlew.bat spotlessApply build`——一起执行 `spotlessApply`（自愈代码格式）与 `build`（编译+重映射+打包），一条命令完成。
3. **沙箱限制**：`java` 会写 `C:\ProgramData\Oracle\Java\...`，构建必须在沙箱外执行（关闭沙箱）。
4. **成功判定**：以日志出现 `BUILD SUCCESSFUL` 为准；PowerShell 管道把 javac 警告（stderr）误报为 `NativeCommandError` 导致的非零退出码不代表构建失败。

### 规则 19：版本号规则与多处同步

本项目版本号采用 `主.次.阶段.序号`（如 `3.4.beta.9`），定义于 `gradle.properties#mod_version`，唯一事实源。缺陷修复/小功能在 `beta.N` 递增序号；功能集变更再考虑提升阶段。

- 版本号必须同步到：`gradle.properties`、`启动上下文.md`、`变更历史.md`。
- 禁止沿用旧版本号发布。
- 引进的第三方模组各自保留其原始版本号，禁止改写模组 JAR 内部版本或文件名。

### 规则 20：状态型文档与实际必须一致

「当前状态」类信息——版本号、依赖版本、产物清单、已知问题状态——必须在 `启动上下文.md`、`AGENTS.md` 与**实际文件系统**之间一致。任何状态变更当天同步，发现不一致当天修正。

历史记录型文档（`工作日志.md`、`变更历史.md`、`已知问题.md` 的已解决条目）只追加不改写，用于保留审计轨迹。

状态型文档中出现数字时，必须写明统计口径。

### 规则 21：死代码与无用内容清理

任何改动后删除未使用的 import、未被引用的文件、失效配置与调试残留。删除前按规则 8 备份。

- mixin、Jade/JEI 插件类虽不被直接引用，属于注解扫描或配置加载，删除前必须核对其注册引用，不得误判为死代码；
- 删除 `@Persisted` 字段会破坏旧存档兼容，必须评估迁移。

### 规则 22：文件编码与换行规范

| 文件类型 | 编码 | 换行 |
|---|---|---|
| `.java` / `.json` / `.md` / `.gradle` / `.toml` | UTF-8 **无 BOM** | LF 或 CRLF 均可 |
| `.bat` / `.cmd` | **纯 ASCII** | CRLF |

`.bat` 必须纯 ASCII + CRLF：UTF-8 中文注释配 LF 换行会被 `cmd.exe` 按代码页逐字节误解析，报 `'.' is not recognized` 并**静默跳过关键步骤**。

### 规则 23：下载国外资源前必须先提示用户开启代理

本机访问**境外站点**时必须由用户手动开启代理。已确认本项目构建会访问的境外域名：

- 代码托管与 Maven：`github.com`、`maven.firstdarkdev.xyz`、`maven.quiltmc.org`、`maven.parchmentmc.org`、`maven.saps.dev`、`maven.tterrag.com`、`maven.blamejared.com`、`cursemaven.com`、`maven.architectury.dev`、`maven.izzel.io`、`maven.teamresourceful.com`、`repo.maven.apache.org`、`services.gradle.org`、`plugins.gradle.org`

执行要求：

1. **先提示，后下载**。任何需要访问境外网络的命令执行**之前**，先提示用户「需要访问境外站点，请确认代理已开启」，并说明要访问哪个域名、为了什么。
2. **不自行配置代理**。本机未设置代理环境变量；用户使用的是系统级代理。**禁止**自行给命令加代理参数。
3. **代理关闭时的失败形态**：连接超时或 `Failed to connect to github.com:443`。遇到这类错误先提示用户开代理并重试，**不要**改脚本或换镜像源。
4. **可离线完成的工作不受此限**：本地文件操作、`javap`、读 `参考/` 已有克隆、构建（若依赖已缓存）都不需要代理。

### 规则 24：子智能体派发规范

1. **复杂任务拆分子智能体并行**：多文件修改、第三方源码 / 字节码实证、批量文档梳理、独立功能模块实现、构建与解包验证等任务优先拆分并行。根智能体只负责任务拆分、代码整合、冲突裁决、最终验证与结果汇总。
2. **简单改动不必派发**：单文件小补丁、读单个文件、简单确认由根智能体直接完成。
3. **派发消息必须自包含**：写清目标文件 / 目录、验收标准、验证方式与输出格式。全部规则对子智能体同等生效。
4. **共享工作区归属约束**：并行任务涉及同一文件时必须先划清归属。共享状态文档（`AGENTS.md` / `执行规则.md` / `启动上下文.md` / `工作日志.md` / `功能与需求.md` / `已知问题.md` / `API标准.md`）由根智能体统一写入，子智能体只读并汇报结论。
5. **子智能体禁止写准则库根**：草稿放临时目录；任务结束后由根智能体清理。
6. **根智能体最终把关**：子智能体产物必须经根智能体整合、复核并验证后才能报告完成；待游戏内验证项按规则 7 标注。

### 规则 25：子智能体产出必须核对文件哈希

1. **派发前后必须记录共享文档的哈希**：派发前记下共享状态文档的 SHA-256；子智能体结束后**重新计算并比对**。
2. **发现被改动时**：不得直接接受，必须逐条复核改动的正确性，再决定保留或回滚；并把越权行为写入 `工作日志.md` 的「踩坑」行。
3. **派发消息必须写明违反后果**。仅仅写「不要修改 X」不够，必须写明「修改 X 会导致你的产出被判为不合格」。
4. **只读任务不给写权限**：确需写时，只允许写明确指定的**新建**文件，禁止修改已有共享文档。

### 规则 26：本地验证只用静态与构建任务，禁止启动游戏

本机无游戏实例、完整 MC 运行时资源开销大且对智能体无交互价值。因此：

1. **禁止执行任何会启动完整 Minecraft 运行时的 Gradle 任务或命令**：`runClient`、`runServer`、`runData`、`runGameTestServer` 及等价命令。
2. **本地验证只用静态与构建任务**：`compileJava`、`test`、`build`、`spotlessCheck` 等；构建后按规则 14 解包核对。
3. **游戏内验证一律标注「待游戏内验证」**，由用户在有实例的环境中执行；不得以「本地跑过」冒充游戏内验证。
4. **例外**：用户本人运行游戏进程不受本条限制；用户明确指示智能体启动（并已确认实例与环境就绪）时除外。

### 规则 27：跨存档依赖的状态必须持久化

任何跨存档（重进世界、区块卸载重载、服务端重启）必须保留的状态——绑定者 UUID、电压等级、进度、缓存、计数器——必须写入机器自身 NBT（`@Persisted` 字段或显式持久化），禁止依赖第三方节点的恢复时序。

- 旧存档缺失字段时必须有回退逻辑（默认值或按邻近玩家重新绑定）。
- **禁止在装配 / 成型回调里无条件覆写持久化字段**：NBT 恢复发生在构造之后，装配回调中无条件赋值会覆盖玩家已保存的设置（真实故障：某仓的可配置倍率在每次成型时被重置）。

### 规则 28：服务端安全，禁止客户端类在服务端加载

- 客户端专属类（渲染器、界面）必须标注仅客户端，并且**通过 lambda 延迟构造**，禁止使用方法引用（`Xxx::new`）——方法引用会在语句执行时解析构造器句柄，强制加载仅客户端类，在专用服务端抛 `BootstrapMethodError`。
- 机器逻辑留在服务端；渲染与界面留在客户端。
- 引用仅客户端 API 的包必须与其他包隔离。

### 规则 29：改动第三方机器行为必须同步修改其提示文本

用 mixin 或子类覆写修改任何第三方模组注册的机器行为时，必须在同一改动中同步修改该机器的物品 tooltip，明确展示「修改了什么、由什么修改」。

若修改的是「配方类型 / 模式列表」等提示中已声明的条目，必须**改写**对应行内容，不能只追加，否则信息自相矛盾。

### 规则 30：Tooltip 与提示文案规范

- Tooltip 精简，说明**机制**而非显而易见的内容（用户明确不喜欢冗余或明显的提示）。
- 配置界面（如批处理面板）应直接显示中文，不需要悬停才能看到中文。
- 新增配置项优先放配置文件（`ConfigHolder`），除非用户明确要求放 GUI。

### 规则 31：代码内一律不写注释

`src/main/java` 与 `src/test/java` 下的 `.java` 文件，以及 `build.gradle`、`settings.gradle`，一律不写注释：不写行注释 `//`、块注释 `/* */`、Javadoc `/** */`，也不写分区或装饰性分隔线。2026-11-17 已按此口径全量清理，此后任何改动都不得重新添加。

- 说明性内容归位到文档：机制说明写 `docs/`，API 事实写 `API标准.md`，构建约束写 `打包.md`，变更写 `变更历史.md`，任务流水写 `工作日志.md`。
- 已知副作用：Mixin 的 `@Overwrite` 缺 Javadoc 时，Mixin 注解处理器会打印 `@Overwrite is missing javadoc comment`。该提示不影响构建结果（仍为 `BUILD SUCCESSFUL`），**不得**为消除它而补注释。
- 不受约束：`gradle.properties`、`mods.toml`、`*.json` 等配置文件的分区注释。
- 评审口径：源文件内出现任何注释行即视为不合格。
