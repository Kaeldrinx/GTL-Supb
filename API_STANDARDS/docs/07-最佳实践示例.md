## 案例一：请求-响应式网络 API（仿 GTLSUPBJAVA 的 WAP 连接列表）

**场景**：客户端 UI 触发一个操作，服务端校验后返回数据刷新 UI。

**链路**（与 [02-请求响应格式规范](02-请求响应格式规范.md) §1.3 一致）：

```
AEBaseScreenWAPMixin（客户端点击"连接列表"）
  → C2SWAPConnectionPacket(containerId, ACTION_QUERY_LIST)  ← 客户端只组装请求
  → 服务端 handle()：
       enqueueWork {
         L1 sender 判空 → L2 containerId 匹配 → L3 菜单类型校验
         → 委托 WirelessAccessPointWirelessManager.getConnectionTargets()
         → 解析显示名
         → CHANNEL.send(PacketDistributor.PLAYER, S2CWAPConnectionListPacket(containerId, entries))
       }
       setPacketHandled(true)
  → 客户端 handle()：打开连接列表屏幕
```

**要点**：
1. 客户端**永不**直接调用服务端 manager（跨逻辑端禁止）；
2. 关联键 `containerId` 贯穿请求与响应；
3. 业务委托 manager/helper，数据包 handler 只做校验与分发；
4. 响应包字段不可变、携带关联键。

**参考实现**：[C2SWAPConnectionPacket.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/network/C2SWAPConnectionPacket.java) + [S2CWAPConnectionListPacket.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/network/S2CWAPConnectionListPacket.java)。
**模板**：[C2SRequestPacketTemplate.java](../examples/network/C2SRequestPacketTemplate.java)、[S2CResponsePacketTemplate.java](../examples/network/S2CResponsePacketTemplate.java)。

## 案例二：能力接口解耦（仿 GTLSUPBJAVA 的能力接口 → 机器逻辑）

**场景**：机器逻辑按能力接口读取配置/加成，不感知具体机器实现。

**三层设计**：

```
能力常量层   GTCEu 标准 PartAbility（GTLSupbMachines 中声明，供结构识别）
能力接口层   IBatchProcessingMachine.isBatchEnabled()/getBatchSize()  (供逻辑调用，最小方法组)
消费逻辑层   MutableRecipesLogic 通过机器查询能力 → 读取批处理倍率
```

**要点**：
1. 新增能力 = 新增 `PartAbility` 常量 + 新增能力接口，**不修改**机器核心类（OCP）；
2. 逻辑层用接口取数，禁止 `instanceof` 具体实现类（DIP）；
3. 接口最小方法组、Javadoc 写计算规则（ISP + 契约）。

**参考实现**：[GTLSupbMachines.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/common/machine/GTLSupbMachines.java)、[IBatchProcessingMachine.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/api/machine/IBatchProcessingMachine.java)、[MutableRecipesLogic.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/api/machine/logic/MutableRecipesLogic.java)。
**模板**：[PartAbilityTemplate.java](../examples/api-layer/PartAbilityTemplate.java)、[IHatchCapabilityTemplate.java](../examples/api-layer/IHatchCapabilityTemplate.java)。

## 案例三：扩展既有类行为（trait / Mixin）

**场景**：为既有机器类增加能力，但不允许修改核心类。

| 扩展方式 | 适用 | 参考实现 |
| --- | --- | --- |
| trait（组合） | 逻辑可抽取复用 | [MutableRecipesLogic.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/api/machine/logic/MutableRecipesLogic.java)、[ZeroEnergyMultiTypeLogic.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/common/machine/multiblock/ZeroEnergyMultiTypeLogic.java) |
| Mixin（注入） | 必须干预上游行为 | [RecipeLogicProviderMixin.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/mixin/gtceu/recipe/RecipeLogicProviderMixin.java)、[ParallelProviderMixin.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/mixin/gtceu/integration/ParallelProviderMixin.java)（按配方/机器类型决定是否生效） |

**Mixin 纪律**：
1. 按目标模组分目录（mixin/gtceu、mixin/ae2、mixin/ftbquests…）；
2. 注入逻辑必须"按需生效"，避免全局副作用；
3. 侵入面最小，能 trait 不 mixin。

## 反模式清单（Anti-patterns）

| 反模式 | 问题 | 正确做法 |
| --- | --- | --- |
| 客户端直接调用服务端逻辑 | 跨端调用、数据不可信 | 走 C2S 数据包 + 服务端校验 |
| 数据包 handler 写 300 行业务 | SRP 破坏、难测试 | 委托 manager/helper |
| `instanceof` 具体实现做功能判断 | DIP 破坏、新增实现需改逻辑 | 用能力接口 + PartAbility |
| 信任客户端坐标/ID 直接操作 | 越权漏洞 | L4 归属校验 |
| 无关联键的异步回发 | 响应错配 | 携带 containerId |
| 硬编码玩家可见文案 | 无法本地化 | 语言文件 + Component.translatable |
| 空 catch 吞异常 | 问题不可排查 | 降级 + LOGGER.warn/error |
| 协议字段随便增删不升版本 | 新旧端不兼容 | 递增 PROTOCOL_VERSION |

## API 评审清单（提交前逐条过）

### 设计
- [ ] 契约完整（类注释含触发/校验/回发）？
- [ ] 面向接口、最小接口、无硬编码依赖？
- [ ] 命名读名知义、无魔法数字？

### 安全
- [ ] L1~L4 四层校验齐全且静默失败？
- [ ] 逻辑在 enqueueWork 内、setPacketHandled(true) 收尾？

### 健壮
- [ ] 环境异常有降级 + 日志，无空 catch？
- [ ] 单点错误不导致整体崩溃？

### 兼容
- [ ] 新字段向后兼容（has 标记）？
- [ ] 协议/版本变更已处理并记录？

### 文档
- [ ] 中文注释精简、说明"为什么"？
- [ ] 玩家文案走语言文件且 zh/en 键一致？
