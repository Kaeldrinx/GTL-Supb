# 04 · 认证授权流程

> 目标：**只允许合法主体在合法会话中对合法目标执行合法操作。**
> 模组网络 API 场景下，"认证"= 确认请求来自已登录玩家；"授权"= 确认该玩家对目标资源有操作权。
> 本章以 [C2SWAPConnectionPacket.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/network/C2SWAPConnectionPacket.java) 的四层校验链为范本。

---

## 1. 四层校验链（模组网络 API 强制）

所有 C2S 数据包的服务端 `handle()` 必须按下述顺序校验，**任一层失败立即静默返回**：

```
L1 身份（Authentication）   sender 是否有效
L2 会话（Session）          containerId 是否匹配当前打开菜单
L3 类型（Context Type）     菜单/方块类型是否与操作匹配
L4 归属（Ownership）        目标资源是否属于该会话/该玩家
```

### L1 身份校验

- **MUST**：`ServerPlayer player = ctx.get().getSender();` 后立即判空。
- **MUST**：判空失败直接 return（未登录实体/伪造包无 sender）。
- **MUST**：不得信任 `sender` 之外的任何客户端身份字段。

```java
ServerPlayer player = ctx.get().getSender();
if (player == null) return;
```

### L2 会话归属校验

- **MUST**：操作绑定菜单的操作包必须校验 `containerId` 与 `player.containerMenu` 一致，防止**跨会话注入**（玩家 A 伪造玩家 B 的会话号）。
- **MUST**：`player.containerMenu == null` 时直接 return。

```java
if (player.containerMenu == null || player.containerMenu.containerId != msg.containerId) return;
```

### L3 上下文类型校验

- **MUST**：用 `instanceof` 校验菜单/方块的实际类型与操作语义匹配（如打开的是 WAP 菜单才能操作 WAP 连接）。
- **MUST**：类型转换失败即 return，不触发业务。

```java
if (!(player.containerMenu instanceof WirelessAccessPointMenu menu)) return;
if (!(menu.getBlockEntity() instanceof WirelessAccessPointBlockEntity wap)) return;
if (wap.getLevel() == null) return;
```

### L4 归属/越权校验

- **MUST**：涉及他人资产的写操作（传送、销毁、领取、修改）必须校验目标确实属于该会话上下文（如目标坐标存在于当前 WAP 连接列表）。
- **MUST**：对越权目标静默拒绝，不回包不提示（防探测攻击）。
- **MUST NOT**：直接信任客户端提交的目标坐标/资源 ID。

**项目正例**：[C2SWAPConnectionPacket.java](../GTLSUPBJAVA/src/main/java/com/gtlsupb/gtlsupb/network/C2SWAPConnectionPacket.java) `resolveAndVerifyTarget`——目标必须在 `getConnectionTargets(wapGpos)` 列表中才放行。

## 2. 授权语义

### 2.1 最小权限

- **SHOULD**：每个动作只校验它需要的归属维度（查询只校会话，跳转/取消才校目标归属），不做过度拦截。
- **MUST**：按动作分发（switch action），动作之间权限独立，不可因一个动作通过就放行全部。

### 2.2 资源模型

- **SHOULD**：为敏感资源建立"所有者"概念：资源归属 = 创建者 / 会话 / 团队（如 FTB Quests 的 team 维度）。
- **SHOULD**：跨团队操作前查询资源所属 team 并校验成员关系（参考 FTB Quests TeamData 的读取模式 [TeamData_full.txt](../GTLSUPBJAVA/libs/ftbq_extract/TeamData_full.txt) 的提取目的）。

### 2.3 服务端权威

- **MUST**：所有授权判断在服务端线程（enqueueWork）内完成；客户端 UI 的"可用/不可用"仅作体验提示，不是安全边界。
- **MUST**：状态缓存（如 AE 任务设置）的读写入口在服务端，客户端只读展示。

## 3. 对外 HTTP API（行业兼容，供扩展）

> 未来对外服务按此对齐：OAuth 2.1 / JWT 为主流。

| 环节 | 约定 |
| --- | --- |
| 认证 | Bearer Token（JWT），`Authorization: Bearer <token>` |
| 授权 | 基于 scope（最小权限声明），资源级 ACL 校验在服务端 |
| 令牌生命周期 | access token 短时（≤1h）+ refresh token 轮换；`exp`/`iat` 必填 |
| 校验 | 服务端校验签名、过期、scope，禁止信任客户端传参身份 |
| 审计 | 敏感写操作记录 `traceId + 主体 + 资源 + 动作` 审计日志 |

---

## 4. 反模式清单

- ❌ 信任客户端传入的玩家名/UUID 作为身份；
- ❌ 只校验类型不校验归属（如校验是 WAP 菜单但放行任意 WAP 的连接操作）；
- ❌ 校验失败抛异常暴露校验细节（泄露规则）；
- ❌ 服务端逻辑写在客户端线程；
- ❌ 无 `setPacketHandled(true)` 导致网络线程异常。

---

## 5. 检查清单

- [ ] L1：sender 判空；
- [ ] L2：containerId 与会话匹配；
- [ ] L3：菜单/方块类型校验；
- [ ] L4：目标归属校验（写操作必查）；
- [ ] 校验失败静默 return、不回包；
- [ ] 逻辑在 enqueueWork 内、setPacketHandled(true) 收尾；
- [ ] 敏感操作有审计日志（对外 API）。
