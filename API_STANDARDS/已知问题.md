## 已解决问题

### GTLSUPB-061：基类类型数组与 provider / EU 重试状态

**发现日期**：2026-11-23

**现象**：多类型线圈/并行舱机器未覆写 `getRecipeTypes()`；provider 在卸载时无条件注销；零能耗机器 EU 转账失败后每 tick 重试并构造 BigInteger；独立槽空配方无判空；类型缓存不随订阅更新失效。

**根因（确定）**：多类型机器只提供 `getRecipeTypeList()`；provider 没有注册状态字段；EU 重试没有节流间隔；缓存字段没有统一失效点。

**影响**：绑定配方类型误判、provider 计数误减、空闲机器持续 tick 开销、潜在空指针。

**修复**：两个多类型基类返回构造时的 `GTRecipeType[]`；provider 增加 `providerRegistered` 并只对已注册实例注销；owner 自动绑定后 `markDirty()`；EU 失败重试降频到 20 tick 并处理 `Long.MIN_VALUE` 首值；独立槽空配方跳过；类型缓存在订阅更新与模式切换时清空。

**验证**：`spotlessApply build` 成功，`recipeSafetyTest` 32/32，产物解包确认字段与方法存在；游戏内待验证。

### GTLSUPB-059：机器成型/空闲空转延迟

**发现/解决日期**：2026-11-06（多轮收敛；"装了维核样板总成才空转、灵珠/魔丸不空转"是定位关键）

**根因（确定）**：① **`patternFingerprint()` 每 tick 全量 NBT 哈希**——旧实现只在"同一游戏刻"内记忆指纹，而指纹是把全部样板槽 `ItemStack.hashCode()`（递归整包 NBT）逐槽哈希；`getSlotBoundRecipes()` 的缓存校验每次搜索都要比对指纹，于是装了样板总成的机器每 tick 首次读取都要重哈希 54 槽 NBT，机器一多就是全服级空转。灵珠/魔丸没有样板槽，所以感受不到——与用户观察完全吻合。② 开批循环按槽位数（默认 8）把同一条搜索跑 N 遍（已改为每 tick 一次）；③ 搜索完成后不消费 `recipeDirty`（已改为消费后退订）；④ 样板总成推料不唤醒控制器（已加推料唤醒 Mixin）。

**解决**：① `patternFingerprint()` 记忆窗口放宽到 40 tick，`onPatternChange` 立即清记忆（样板内容变化下一拍即重建绑定缓存）；② 每 tick 至多一次 `findBatch()`；③ 搜索完成后 `recipeDirty = false`；④ `MEPatternBufferPushPatternMixin` 推料后 `markLastRecipeDirty()` + `updateTickSubscription()`。

### GTLSUPB-058：并发批次跨配方并行失效 / 合并无界

**发现/解决日期**：2026-11-06（多轮收敛；"跨配方不是处理无限种配方"为最终口径）

**根因（确定，对照 gtlcore/GTLAdditions `MultipleRecipesLogic`）**：跨配方并行 = 一条合并配方在**一份并行预算内**逐候选顺序吃满（`remain = maxParallel × threads`，预算吃尽即不再扩入新配方）。此前两轮分别错在：候选收窄成一条（拆散合并）、并行池设为无上限且每配方独立拿满额（合并可扩入无限种配方，总量超过机器能力）。

**解决**：并发批次路径预算 = 机器结构并行（每条批次一份独立预算，多批次 = 多份）；池内候选**轮转排序 + 顺序吃满**，不按候选数平摊（`calculateParallel` 跳过 `boundCandidateCount` 平摊）；预算吃尽即停止扩入新配方。单配方路径（`concurrentThreads == 1`）保持 gtlcore 共享池口径（结构并行 × 线程数）。

### GTLSUPB-057：打包样板按钮压住网络状态显示

**发现/解决日期**：2026-11-06

**根因（确定）**：状态文字用 `new LabelWidget(8, 2, Supplier<String>)` 直接把 gtceu 语言键**当字符串原文渲染**（约 130px 宽），页头被占满，按钮放哪都会压住它。

**解决**：状态文字改用本模组短键 `gtlsupb.gui.me_network.online/offline`（"在线/离线"，≤46px，tooltip 保留完整状态）；打包按钮固定在 `[uiWidth-126, 2, 44×12]`（右侧重命名框从 `uiWidth-78` 开始），两种语言下三段互不重叠。

### GTLSUPB-060：FTB 任务检测 / 奖励入 AE / 从 AE 提交失效

**发现/解决日期**：2026-11-06

**根因（确定）**：三者都依赖 `AEGridRegistry.getActiveGridsForPlayer(uuid)`，而该查询会直接跳过"无归属记录"的网格。归属只由 `AEGridTrackerService.addNode` 记录；若 GridServices 注册失败 / 版本偏斜导致回调不触发（或仅由 `MEDrivePartMachine` 兜底注册），所有网格都无归属 → 查询永远为空 → 三个功能一起失效。

**解决**：查询时对无归属网格按需从 `IGrid.getNodes()` 补记归属（`IGridNode.getOwningPlayerProfileId()`，与 tracker 同一数据源），补记后仍无归属才排除；多玩家分隔语义不变。

### GTLSUPB-029：彩虹渐变效果不满意

### GTLSUPB-032：时序推演模块样板端口无法打开

**发现/解决日期**：2026-11-04

**根因**：gtlcore 的 `MECraftPatternContainerPartMachine` / `MEMolecularAssemblerIOPartMachine` 在 `addedToController` 后把 `shouldOpen` 置为 false，端口界面只允许由量子编织主一类的控制器统一提供；时序推演模块没有对应控制器界面。

**解决**：新增两个 gtlcore Mixin，仅当控制器为 `ChronoDeductionArray` 时让 `shouldOpenUI` 返回 true，恢复样板核心与分子操纵端口的自带界面；其它主机保持原行为。

### GTLSUPB-033：虚空能源吸收器发电异常

**发现/解决日期**：2026-11-04

**根因**：每 tick 已把 `V[tier]` 注入内部储能，又每 20 tick 额外广播 `V[tier]×20`，同一份电被重复计算；满储能且开关关闭时退订 tick，线缆放空后永不恢复；广播按 `remaining/100` 分配，接收者少时几乎分不出去；Jade 把“广播剩余量”当发量显示。

### GTLSUPB-002：批处理开启时机器误报「材料输入不足」且无法运行

**发现日期**：2026-09-17　**解决日期**：2026-09-17（3.4.beta.9）

**症状**：开启批处理（默认启用，倍率上限 100）后，机器显示「材料输入不足」（`RecipeResult.FAIL_INPUT`），无法启动。

**根因（确定，两条叠加）**：

1. **多配方合并超领**：装配期每个配方独立用 `matchRecipeInput` 校验（均通过），再把输入聚合进合并配方。多个配方复用同一批原料时，聚合总量超过仓内实际存量，最终合并配方校验失败 → 误报「材料输入不足」。
2. **批处理非自适应**：`getBatchSize()` 恒返回配置上限 100，批处理块是「固定 ×100 或 ×1」的二元判定。无限并行机器合并配方已吃满库存时 ×100 必然失败而退化为不批处理——批处理永不生效；且倍率从不在输入/输出允许范围内降档。

**处置**：

- `processParallelDataNormal` / `processParallelDataWireless`：装配期改为**逐配方聚合输入 + 增量 matchRecipeInput 校验**（`accumulateInputsIfFit`），放不下的配方让位于先入列配方，保证合并配方输入始终可一次取齐。
- `buildNormalRecipe` / `ZeroEnergyMultiTypeLogic` / `SteamUniversalModule`：批处理改为**自适应**（`findFeasibleBatch` 折半搜索最大可行倍率 N ≤ 上限，按输入/输出可取量降档）。

**验证**：三次构建（spotlessApply + build）全部 `BUILD SUCCESSFUL`；解包核对 `RecipeCalculationHelper` 含 `findFeasibleBatch` / `accumulateInputsIfFit` / `batchFits`。**游戏内效果待验证**。

### GTLSUPB-004：机器空转/延迟 —— 搜索路径上的一系列负优化

**发现日期**：2026-11-02　**解决日期**：2026-11-02（3.9.18）

**症状**：机器补批慢、`[配方查询]` 实测单次搜索 4~19ms、2 分钟 225 次搜索但批次仅 1/8；服务器偶发落后。

**根因（对照 gtlcore 源码逐项核实，非推测）**：

1. **候选过多**：每次搜索收集最多 256 条候选并逐条并行核算；gtlcore 的 `gtlcore$searchRecipe` 命中首条即返回（候选数 = 1）。单次成本 ≈ 候选数 × 单次匹配。
2. **谓词含输出匹配**：`checkRecipe` 用 `matchRecipe`（输入 + 输出），而输出在投料 `admitBatch` 与结算阶段本来就会再校验一次 —— 每次匹配成本翻倍。
3. **查两遍**：绑定路径 `checkRecipe` 失败后又调一次 `matchRecipe` 只为拼日志文案。
4. **高频搜索**：扣料失败每 2 秒重搜、自愈每 60 秒全量失效样板绑定缓存并重解析 NBT；上游用 WAITING 保活 + 通知唤醒。

1. `HypercubeCoreTowerLogic.buildFinalNormalRecipe()` 对整条 `baseRecipe` 执行
   `copy(ContentModifier.multiplier(100), false)`，把 inputs 与 outputs 一起放大 ×100。
   共享池模式下 `setupRecipe` 会要求 100 倍材料，输入不足时整批不启动。
2. 蒸汽工厂三处 `connectionCount * 16384` 直接相乘；连接数异常大时 `long` 回绕为负，
   机器得到“负并行”并停摆。

**处置**：聚合塔改用 `RecipeCalculationHelper.applyOutputMultiplier()`（只放大 outputs 与
tickOutputs，inputs 原样保留）；蒸汽并行统一使用 `RecipeSafety.saturatedMultiply()`（溢出饱和到
同号极值），并新增 5 项纯 JDK 断言。

**验证**：`spotlessApply build` BUILD SUCCESSFUL；`recipeSafetyTest` 32/32 通过。**游戏内账目待验证**。

### GTLSUPB-006：独立供线不扣料、零能耗重复扣料、合并产出不预检

**发现日期**：2026-11-02　**解决日期**：2026-11-02

**根因（源码实证）**：

1. `MutableRecipesLogic` 独立供线模式（≥2 个绑定样板槽）构造的合并配方刻意不携带输入，但 `consumeIndependentBoundSlotInputs()` 从未被调用 → 产出有、扣料无。
2. `ZeroEnergyMultiTypeLogic.calculateParallels()` 用 `handleRecipeInput` 先扣一次，合并配方又携带输入交给 `setupRecipe` 再扣一次 → 双倍吃料。
3. GTCEu 默认 `onRecipeFinish()` 会复用 `lastRecipe` 直接 `setupRecipe`；独立供线合并配方无输入，`matchRecipe` 恒成功 → 重复产出且不扣料。
4. `getRecipe()` 启动前不校验输出容量，合并产出超出输出仓时结算阶段被丢弃。

**处置**：`handleRecipeIO(IN)` 内逐槽 `verify+commit` 并 `lastBoundSlots.clear()`；零能耗改 `matchRecipeInput`（只模拟）；`onRecipeFinish` 改为结算后重搜；`getRecipe` 增加 `gtlsupb$outputsFit`（`matchRecipeOutput`）预检；蒸汽扣费移至 `setupRecipe` 成功进入 WORKING 后提交；`markLastRecipeDirty` 重置搜索节流与计划。

**验证**：`spotlessApply build` BUILD SUCCESSFUL；`recipeSafetyTest` 27 项通过；解包核对关键方法与中英语言键。**游戏内效果待验证**。
