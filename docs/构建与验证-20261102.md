## 产物核对

构建后建议用 `jar` / `javap` 抽查关键符号是否入产物，例如：

```powershell
# 看条目
Add-Type -AssemblyName System.IO.Compression.FileSystem
$z=[System.IO.Compression.ZipFile]::OpenRead('build\libs\GTL-Supb-4.5.jar')
$z.Entries | ForEach-Object FullName | Select-String 'mods.toml|mixin.json|refmap|GTLSupb.class'
$z.Dispose()

# 反编译关键类
$javap='C:\Users\Administrator.DESKTOP-N0QCVKS\.jdks\temurin-17\bin\javap.exe'
& $javap -p -classpath build\libs\GTL-Supb-4.5.jar com.gtlsupb.gtlsupb.api.machine.logic.MutableRecipesLogic
```

核对要点：
- jar 内能看到 `META-INF/mods.toml`、`gtlsupb.mixin.json`、`GTL-Supb-refmap.json`（Mixin refmap 缺失会导致实机注入 NPE）
- 新引入的机器 / 逻辑类（如 `PatternAssemblyPartMachine`、`MultiTypeMutableRecipesLogic`）都要在 jar 里找到

## 2026-11-05 踩坑备忘（请不要再次踩到）

### 1. 不要在 Loom 缓存不完整时用 `--offline`

之前文档里写的是默认加 `--offline`，**这在当前仓库里是错的**。这次构建启动时遇到：

```
"Lock for cache='...\.gradle\caches\fabric-loom' is currently held by pid '13024'.
Locking process does not exist, assuming abrupt termination and deleting lock file.
Found existing cache lock file (ACQUIRED_PREVIOUS_OWNER_MISSING), rebuilding loom cache.
```

上一次构建被打断，残留的 `.62321801b628b287.lock` 里写着已死进程 pid，Loom 判定缓存不可用，整份 `fabric-loom/` 要重建。之后 MCP 10 步里 `downloadClientMappings`、`mergeMappings`、`extractServer` 全都要联网（`piston-data.mojang.com`、`files.minecraftforge.net`、`maven.minecraftforge.net`），`--offline` 直接把这些下载禁掉：

```
Caused by: net.fabricmc.loom.util.download.DownloadException:
Unable to download https://piston-data.mojang.com/.../client.txt in offline mode
```

**结论**：默认 `build` 就跑**不加 `--offline`** 的那一条。只有在 `fabric-loom/` 目录完整、且 Minecraft / Forge / MCP 三个版本号都没变过时才允许加 `--offline` 提速。

### 2. Loom 重建缓存会很慢，第一次要有心理预期

这次重建耗时 1h19m，主要是：
- MCP 10 步（strip / merge / rename / patch / access transform）
- 对所有 `modImplementation` 依赖做 TinyRemapper（10 个分组、每组长 1.5~6.5 min）
- 跑 `recipeSafetyTest` + jar + remapJar

重建完之后再跑增量 `build` 应该在分钟级。**如果构建在 MCP / remap 阶段慢但 CPU 持续跑着，不要中途 kill，大概率再等几分钟就好。**

### 3. 锁文件残留的清理方式

当 Loom 启动时提示 `Found existing cache lock file (...), rebuilding loom cache`，构建之前可以先手动删掉残留锁，让本次构建直接走重建，避免中途再触发锁冲突：

```powershell
Remove-Item "$env:USERPROFILE\.gradle\caches\fabric-loom\*.lock" -Force -ErrorAction SilentlyContinue
```

### 4. 排查 Loom 下载卡住的手段

- `jstack <gradle-daemon-pid>` 看是否有线程卡在 `sun.net.www.protocol.https.HttpsClient.afterConnect` / `sun.security.ssl.SSLSocketImpl.startHandshake`——那就是 TLS 握手没响应，一般再等几分钟自己会好；如果 10 分钟以上还不动，再检查代理 / 换一条网络。
- `Get-NetTCPConnection -OwningProcess <pid>` 可以看 Gradle 守护进程有没有对外的 HTTPS 连接。
- 独立用 curl 和 Java 分别测目标 URL：`curl.exe https://piston-data.mojang.com/.../client.txt -o NUL` 和一个最小的 `HttpURLConnection` 小程序。两者都通、但 Loom 还不动，那大概率是 TLS 握手等待，不是网络不通。
