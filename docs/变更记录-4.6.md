# 变更记录 — 4.6（配方逻辑空转与跨配方并行根因修复）

日期：2026-11-06

## 一句话

把扣料从搜索阶段移到批次启动阶段（扣料与开跑 1:1）、断开"状态翻转 → 置脏 → 全池重搜"的自唤醒链，并**保留一条批次内的跨配方并行**（一次开批合并当前全部可执行配方）。

## 演进（三轮，避免误读旧结论）

| 轮次 | 方向 | 结论 |
|---|---|---|
| 一 | 一批一配方（每批次只跑一条候选） | **已撤销**。实机表现为"并发批次只跑一个配方"—— 用户要的是**一条批次内同时跑多种配方**，不是多条批次各跑一种 |
| 二 | 空闲搜索节流 / Host 复用 / 槽位缓存 / 输出受阻重试节流 | 保留 |
| 三 | 恢复"合并语义"（一条批次 = 全部可执行候选）+ 扣料按实际采纳裁剪 + 维核样板总成降开销 | 保留 |
| 四 | 无限机器空转（`keepSubscribing` 恒 true）+ 首条候选吃满库存导致其余配方落选 | 保留 |
| 五 | 寰宇通用厂与零能耗机器的常驻 tick 订阅 + 蒸汽系机器跨配方 + 一批"配方跑不起来"的准入条件 | 保留 |
| 六 | 部件级周期任务降频（自适配仓找玩家、模块扫描、催化剂补货）+ 无线离线判定前移 | 当前实现 |

详见文末「第三轮」一节。下文第一、二节保留的是三轮累计的根因与改法，其中"一批一配方"相关表述已被第三轮取代。

## 根因（对应代码事实）

| # | 现象 | 根因 |
|---|---|---|
| 1 | 空闲机器持续吃 tick | 批次模式下 `gtlsupb$searchBudget()` 返回 `Integer.MAX_VALUE`，`recipeQueryBudget`/`HARD_CANDIDATE_CAP` 全部失效；每次唤醒都对整机配方池逐条 `matchRecipeInput` 全模拟 |
| 2 | 机器无法退订休眠 | `updateTickSubscription()` 无条件 `recipeDirty = true`，而 GTCEu 的 `setStatus()` 在状态变化时内部就会调它 → `WORKING/WAITING/IDLE` 每次翻转都重新武装一次搜索，`sleepWhenIdle()` 被自己的脏标记挡住 |
| 3 | 并发批次"不支持跨配方并行" | `gtlsupb$calculateBatchParallels()` 遍历**全部**候选并逐条真扣，合并成 **一条**配方 → 第 1 个槽位吃光材料，`slots` 恒为 1 |
| 4 | 跨配方时"只跑一种/料没少" | 覆写 `calculateParallels()` 的机器（灵珠/魔丸/炼金炉等）绕过了搜索期扣料，而 `skipInputs` 无条件按 `gtlsupb$batchSearch` 置真 → 合并配方无输入 → `consumeInputs` 扣 0 料也开批 |
| 5 | 扣了料却没有产出 | 扣料在搜索期完成，`processParallelDataNormal` 的 `shouldBreak` 在合并阶段丢弃后续候选的输出 |
| 6 | 空闲期固定频率空转 | `FragmentWorldCollector` 每 20 tick 无条件补唤醒、`PatternAssemblyPartMachine` 每 40 tick 无条件扫样板槽 + 查 AE |

## 改法

### `api/machine/logic/MutableRecipesLogic.java`

- 新增 `gtlsupb$pendingBatchRecipe`：搜索阶段只"选定一条候选 + 并行放大 + 模拟校验"，**不扣料**；扣料在 `Host#consumeInputs` 真正执行一次，扣成功才入列。
- `gtlsupb$calculateBatchParallels()` 拆成 `gtlsupb$pickSingleBatchRecipe()`（共享池，取第一条可执行候选）与 `gtlsupb$pickSingleBoundSlot()`（独立供线，取第一个可执行槽位），两者都只返回 **一条** 配方。
- `gtlsupb$searchBudget()`：批次模式改为 `min(64, queryBudget × slots × 4)`，不再全池扫描。
- 新增 `setStatus()` 覆写 + `gtlsupb$inStatusChange`：状态翻转期间屏蔽 `updateTickSubscription()` 的置脏副作用；外部唤醒（来料/样板/结构）仍照常置脏。
- `buildFinalNormalRecipe()` / `buildFinalWirelessRecipe()`：`skipInputs` 改为按 `gtlsupb$pendingBatchRecipe != null` 判定（即"搜索期有没有真扣过料"），覆写类因此恢复"合并配方自带输入 → consumeInputs 真扣"。
- 输出容量预检恢复覆盖批次路径（扣料已延迟，预检失败时未扣任何材料）。
- 新增 `gtlsupb$isBatchSearch()` 供子类判断批次语义；`getConcurrentThreads()` 每 tick 只算一次。

### `api/machine/logic/ConcurrentBatches.java`

- 语义与注释统一为"一批一配方"；补批保持每 tick 一条（一次 `findBatch()` = 一次搜索，同 tick 连补 N 次等于搜索成本 ×N）。

### 子类（一批一配方）

- 共享池：`ZeroEnergyMultiTypeLogic`、`LingZhuMachine`、`MoWanMachine`、`AlchemicalForgeMachine`、`NoEnergyIntegratedProcessorLogic`、`FragmentWorldCollectorLogic`、`SteamUniversalModule` 在"首条可执行配方入列"后 `break`；`MicrocosmFoundryModuleBase` / `ForgingShipModuleBase` 按轮转顺序逐条尝试，只返回第一条。
- 逐槽独立供线：`ZeroEnergyMultiTypeLogic` / `SteamUniversalModule` 在批次模式下改走 `gtlsupb$pickSingleBoundSlot()`（一批一槽位），并让 `buildFinalNormalRecipe()` 在批次路径**不再**重算 `calculateIndependentBoundParallels()`（否则会把全部槽位重新灌回来）。蒸汽模块把蒸汽核算抽成 `gtlsupb$stageSteamFor(ParallelData)` 以复用。

### 空转闸门

- `FragmentWorldCollector`：空闲补唤醒加配额（`SELF_HEAL_MAX_WAKES = 5`），用尽后停止；重新开跑清零。此前该探针让机器**永远无法退订**。
- `PatternAssemblyPartMachine`：控制器全部空闲时催化剂补货间隔由 40 tick 降到 200 tick，有控制器开跑立即恢复。

## 玩家可见行为变化

1. 并发批次现在会真正出现多条：不同配方各占一个槽位、各自进度/结算（此前恒为 1 条合并批次）。
2. 槽位按 tick 递增填满（默认 8 槽 ≈ 8 tick），不是同一 tick 全部出现。
3. 灵珠/魔丸/炼金炉等机器在**非**逐槽独立供线（绑定样板槽 < 2）时会正常扣料 —— 此前可免料产出。
4. 输出满时不再先扣料：机器停在"输出受阻"，材料留在仓里。
5. 空闲机器真正退订：不再每 20 tick / 每 2 秒重复全量搜索。

| 项 | 旧 | 新 |

## 第三轮（同日，恢复跨配方并行 + 维核样板总成降开销）

### 1. 一条批次内跨配方并行（撤回"一批一配方"）

| 环节 | 做法 |
|---|---|
| 取配方 | `gtlsupb$collectBatchParallels()`：遍历全部候选，**逐条核算 + 聚合模拟校验 + 全部收进同一条批次**；并行池不分摊（每条候选独立吃满结构并行） |
| 输入聚合 | 用 `accumulateInputsIfFit` 逐条累加探针（与合并阶段同口径），保证"多条候选抢同一批料"时合并配方仍能一次取齐 |
| 扣料 | 仍延迟到 `Host#consumeInputs`：先整批 `matchRecipeInput` 预检，再逐条真扣；一次开批只扣一次 |
| 一致裁剪 | `ProcessParallelDataNormalResult` / `WirelessResult` 新增 `acceptedIndices`，合并安全阀（`shouldBreak`）丢掉尾部候选后，`gtlsupb$prunePendingBatchRecipes()` 同步裁剪扣料清单 —— 不再"扣了料却没产出" |
| 独立供线 | 批次路径恢复 `calculateIndependentBoundParallels()`（全部槽位一次并入），但**保留逐槽 `verifySlotBoundRecipes` 预校验**：失败槽位只跳过自己，不再毒化整批 |
| 子类 | `ZeroEnergyMultiTypeLogic` / `LingZhuMachine` / `MoWanMachine` / `AlchemicalForgeMachine` / `NoEnergyIntegratedProcessorLogic` / `FragmentWorldCollectorLogic` / `SteamUniversalModule` / `MicrocosmFoundryModuleBase` / `ForgingShipModuleBase` 撤回"首条即 break"的收窄，恢复收集全部候选 |

### 2. 维核样板总成的 tick 开销

| 项 | 旧 | 新 |
|---|---|---|
| 绑定槽位核算 | 每条绑定配方都遍历**全部**部件 × **全部**槽位；一次搜索 O(绑定数 × 槽位数) | 每次搜索只建一次"配方 → 绑定槽位"索引（O(槽位数)），之后每条配方只看自己的槽位（`gtlsupb$ensureBoundSlotIndex`） |
| 绑定候选准入 | `RecipeRunnerHelper.matchRecipe`（输入 + 输出全模拟） | `checkRecipe`（只校验输入）；输出由 `gtlsupb$outputsFit` 在启动前统一预检 —— 每次搜索省掉一遍全量输出匹配 |
| 存量表读取 | 每次调用 `new LinkedHashMap<>(cache)` 拷贝 | 缓存命中返回 `Collections.unmodifiableMap(cache)`，零拷贝 |
| 催化剂补货节拍 | 每 tick 调 `anyControllerActive()`（遍历控制器），再按 40/200 tick 决定是否补货 | 每 tick 只做计数；活跃度判定与补货都在 40 tick 节拍上，空闲时再跳 4 拍（200 tick 一次） |

## 第四轮（同日，无限机器空转 + 首条吃满库存）

### 1. 无限机器空转的根因：`keepSubscribing()` 恒 true

`ZeroEnergyMultiTypeMachine`（墟渊化学蚀骸仪、寰宇通用厂、碎界采集器等所有零能耗机器）覆写了：

```java
@Override
public boolean keepSubscribing() {
    return true;   // ← 旧实现
}
```

而 `MutableRecipesLogic.gtlsupb$sleepWhenIdle()` 的第一道闸门就是它：

```java
if (getMachine().keepSubscribing() || recipeDirty || lastFailedMatches != null) return;  // 不退订
```

`true` 意味着**永远不退订** → 机器空闲时仍每 tick 被 `serverTick` 回调（调度器空转 + 每 5 tick 一次搜索）。
灵珠/魔丸继承 GTCEu 的 `MutableCoilElectricMultiblockMachine`，`keepSubscribing()` 默认 `false`，
空闲即退订 —— 这正是"无限机器空转、灵珠魔丸不空转"的差别所在。

改为 `false`。唤醒链已完整覆盖：控制器自身电路槽/模式槽 → `onChanged()`；
输入仓放料 → GTCEu 部件 handler 的 changed listener；样板推料 → `gtlsupb$wakeControllers()` /
`MEPatternBufferPushPatternMixin`（都调 `markLastRecipeDirty`）。

### 2. 每条批次只跑一种配方：首条候选把库存"账面吃满"

`calculateParallel()` 对每条候选**独立**按当前库存算并行：

- 无限并行机器（`getMaxParallel() == Integer.MAX_VALUE`）→ `pMax = 库存 / 单份需求`，即"能跑多少份全给我"；
- 第一条候选据此拿到全部份数，聚合探针（`accumulateInputsIfFit`）的账面被它占满；
- 第二条（哪怕材料不同、或同材料只分一小份）在聚合校验里直接落选 → 批次里只剩一条配方。

修法（`gtlsupb$collectBatchParallels`）：逐条核算后**给后面尚未处理的候选预留保底份额**再聚合：

```java
long remaining = Math.max(0, total - 1 - i);
long reserve = Math.min(remaining, pMax / 4);   // 预留上限 = pMax/4，本条至少保留 75%
long p = Math.max(1L, pMax - reserve);
```

预留后仍放不下时退到保底 1 份再试一次（连 1 份都放不下才跳过 —— 说明该材料确实被前面的候选吃光）。

同时 `ZeroEnergyMultiTypeLogic.calculateParallels()` 不再自己维护一份"逐条按全部库存算并行"的循环，
改为直接复用 `gtlsupb$collectBatchParallels()`，两条路径的口径保持一致。

## 第五轮（同日，寰宇通用厂空转 + 配方准入 + 蒸汽系跨配方）

### 1. 寰宇通用厂仍然空转：多余的 20 tick 周期订阅

`UniversalFactoryMachine` 除了配方逻辑，还挂了一个自续订的 `tickSync`：

```java
private void tickSync() {
    if (this.getOffsetTimer() % 20 == 0) syncClientData();   // 只是重算电压等级
    syncSubs = subscribeServerTick(syncSubs, this::tickSync); // ← 永远续订
}
```

配方逻辑退订后**它仍让机器每 tick 被回调**。而 `computeVoltageTier()` 在这些时机已经足够新：
结构成形 / 读档 / 自动绑定 / 数据棒绑定、每次并行核算（`getMaxParallel()`）、打开 GUI。
→ 整条 `tickSync` / `subscribeSync` / `syncSubs` 删除。

顺带给 `computeVoltageTier()` 的无线分支加了 10 tick 解锁等级缓存：配方准入谓词对**每条候选**
都会问一次电压等级，原实现每次都查 `VoltageUnlockManager`。

### 2. 其他依旧常驻 tick 的机器

`ZeroEnergyMultiTypeMachine.gtlsupb$tickGeneratedEu` 原本每次末尾无条件自续订 → 所有零能耗机器
永久每 tick 回调。改为**按需**：只有 `generatedEuBuffer > 0` 或仍在找归属玩家时才续订，
否则退订；下一次产电由 `gtlsupb$addGeneratedEu()` 重新挂上。自动绑定玩家加了 20 次配额
（约 20 秒），用尽后改由数据棒手动绑定，不再永久扫描在线玩家。

### 3. 蒸汽系机器跨配方并行

`NoEnergyIntegratedProcessorLogic`（蒸汽能矿石处理中枢）与 `SteamUniversalModule`
都是"逐条核算 + 逐条扣蒸汽"，但并行上限来自**蒸汽池余额 / 单份蒸汽**，第一条会把池子算满，
后续配方在合并阶段的聚合校验里全部落选。修法与共享池一致：按轮转顺序展开候选，
给后面尚未处理的候选预留保底份额（`reserve = min(剩余条数, p/4)`）。

### 4. 让配方"跑不起来"的准入条件（审查后修正）

| 位置 | 问题 | 修法 |
|---|---|---|

### 0. gtlcore 的实现对照（结论先行）

反编译 `org.gtlcore.gtlcore.common.machine.trait.MultipleRecipesLogic`：

**关于"自愈是否需要"**：gtlcore 机器没有任何自愈探针 —— 它靠 GTCEu 原生唤醒链

保留的自愈只作为"AE 推料不穿透到控制器"的补偿（gtlcore 用 mixin 在 `pushPattern` 后唤醒，我们同样做了）。

### 1. ME 输入总成 / 输入总线"识别不到材料"：聚合探针把电路堆在一起

`accumulateInputsIfFit` 把多条候选的 `inputs` 直接 `addAll` 成一个聚合探针。
**电路是每配方一份的配置项，不是可累加材料** —— 多条候选各有不同电路时，聚合探针里会同时出现
多个电路配置，`getSharedCircuitInventory().handleRecipeInner(...)` 必然失败，整批候选被判"缺料"。
外部表现就是"机器看不到 ME 输入总成/输入总线里的材料"。

修法与 gtlcore 的 `ingredientsMapWithoutCircuit` 对齐：聚合时**剔除集成电路项**
（`IntCircuitBehaviour.isIntegratedCircuit`），电路由候选准入时的单条 `checkRecipe` 负责。
影响面：所有走 `accumulateInputsIfFit` 的路径（批次收集、合并、蒸汽系）。

### 2. 蒸汽能矿石处理中枢 / 蒸汽通用工厂：跨配方仍只跑一种

两处 `calculateParallels` 用逐条 `matchRecipeInput` 校验（各自看库存、互不感知），
合并阶段才做聚合 → 第一条把库存账面吃满 → 后续整批落选。

改为在 `calculateParallels` 阶段就用 `accumulateInputsIfFit` 聚合探针（与合并阶段同口径），
配合已有的 `reserve = min(剩余条数, p/4)` 预留，让后续配方既能进批次、又不会超量。

### 3. ME 驱动器拉取开销

`tryPullCells()` 要遍历**整个 AE 网络缓存**（种类可达上万）并逐项找空槽，原实现固定每 20 tick 一次。
改为自适应退避：上次一个元件都没拉到 → 间隔翻倍（上限 200 tick）；拉到 → 立即回到 20 tick。
玩家新插元件最迟 10 秒内被拉取。网格注册（便宜）仍保持 20 tick。

### 4. 运行中接收新订单（结论）

合并语义下，一条配方在 `setupRecipe` 时内容就固定了，运行中推入的新材料**不会**并入当前配方。

### 2. 蒸汽能矿石处理中枢 / 蒸汽通用工厂：蒸汽池不再被首条吃满

两处 `calculateParallels` 里 `steamParallel = availableSteam / steamCost` 是**递减式**分配：
第一条按全额池算并行 → `availableSteam -= p*cost` → 后续 `steamParallel = 0` 直接 `continue`。
即使加了 `p/4` 预留也没用（蒸汽量大时预留份数远小于一条配方的消耗）。

改为**按候选数预留蒸汽**：

```java
long reserveSteam = min(availableSteam, (剩余候选数) * steamCost);
long usableSteam  = max(0, availableSteam - reserveSteam);
long steamParallel = usableSteam / steamCost;
if (steamParallel <= 0 && availableSteam >= steamCost) steamParallel = 1;  // 保底 1 份
```

每条候选都先给后面留 1 份，剩下的才归自己 → 池子够时每条都吃满，池子紧时至少每种配方各跑 1 份。
扣费口径不变（`availableSteam -= p*cost` 仍按实际分配量递减，不会超支）。

### 3. GTLAdditions-3.3.1Custom 为什么吃内存（分析结论）

**主因：`GTRecipeLookupMixin.getRecipeIterator()` 每次配方搜索都重建 ME 缓存配方列表。**

```java
var parts = rlm.getMEPatternRecipeHandleParts();   // 每次遍历部件
List<GTRecipe> meRecipes = new ObjectArrayList<>();
for (var part : parts) meRecipes.addAll(part.getCachedGTRecipe());   // 全量拷贝①
meRecipes = meRecipes.stream().filter(r -> r.recipeType == recipeType).toList();  // 全量拷贝②
```

一次搜索至少分配两个列表，内容是**所有样板仓缓存配方的全量**（不按类型预分组）。
8 仓 × 每仓上千条缓存配方时，一次搜索拷贝上万引用；搜索每 5 tick 一次、机器一多，GC 压力呈线性放大。

**次因**：

1. `MultipleRecipesLogic.getRecipe()` 对每条候选 `recipe.copy(ContentModifier.multiplier(p), false)`
   + `IParallelLogic.getRecipeOutputChance()` 再 copy 一次 —— 每条候选 2 个大对象，
   而候选数是"配方池里有料的全部"。
2. `MEItemInputHandlerBase.prepareMEHandleContents()` 每次处理都新建 `Object2LongMap` 并
   `AEUtils.ingredientsMapWithoutCircuit` 重建 map。
3. `getMEPatternRecipeHandleParts()` 每次遍历部件列表（没有缓存）。

**对照本项目的做法**（已避开）：

- `gtlsupb$ensureBoundSlotIndex()`：每次搜索只建一次「配方 → 绑定槽位」索引，之后复用；
- 候选收集有 64 条硬上限，不会按配方池全量展开；
- 聚合输出用 `LinkedHashMap` + `BigInteger` 累加，不逐条复制配方。
