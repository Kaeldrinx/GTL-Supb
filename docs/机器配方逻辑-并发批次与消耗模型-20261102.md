# 机器配方逻辑：并发批次与消耗模型 — 2026-11-02

## 原因

3.9.18 迭代中，机器配方逻辑经历了"单条合并配方"与"逐条就地消耗"两轮改造，暴露出三个问题：

1. **产出数量与请求不一致**：请求 1000 个产物只产出 250，剩余材料被消耗却不转化为产物；
   开批处理后变成 1.25k，掩盖了基础错配。
2. **并发批次失效**：运行配方 A 时新投入的配方 B 无法开始，必须等 A 完成。
3. **合成延迟变大**：每 tick 都触发全量配方搜索，tick 开销与响应延迟同时上升。

## 根因

- **扣料与开跑不 1:1**：扣料被提前到 `getRecipe()` 构建阶段，而 `getRecipe()` 会被多次调用
  （取配方、结算前重取、启动重试），一旦扣料后没有真正开跑（能量不足/维护/`beforeWorking` 被拒），
  材料即消失 → 消耗 N 份、只结算 1 份（250 = 1000 ÷ 4）。
- **单条 `lastRecipe`**：只有一个运行配方，无法承载 A/B 同时运行。
- **每 tick 搜索**：`handleRecipeWorking` 每 tick 调一次取配方，含并行核算的全量搜索。

## 修正

恢复"并发批次"运行模型，并约束扣料与开跑严格 1:1：

| 环节 | 实现 |
|---|---|
| 批次载体 | `RunningBatch { recipe, duration, progress }`，列表上限 = 合并预算（配置 `concurrentThreads`，1~16） |
| 取配方 | `gtlsupb$buildSingleBatchRecipe()`：**一条批次只含一条配方**，并行只按该配方自身可用材料核算 |
| 扣料 | `startOneBatch()`：`matchRecipeInput`（模拟）→ `handleRecipeInput`（真扣）→ 入列，**扣料成功才入列** |
| 推进 | `handleMultipleRecipeWorking()` 遍历所有批次：各自 `checkConditions` → 各自扣 tick 输入 → `progress++` |
| 结算 | 到达时长 `settleBatch()` 产出；输出放不下则保留该批次下 tick 重试，不吞产物 |
| 上游兼容 | 多配方模式下 `onRecipeFinish()` 直接返回，避免按"单一 lastRecipe"重复产出 |
| 节流 | `START_INTERVAL_TICKS = 5`：两次"取新配方"至少间隔 5 tick，搜索频率从每 tick 降到每 5 tick 至多一次 |

并行分配算法 `AllocationAlgorithm`（FAIR/GREEDY 二选一）整体移除：FAIR 会把整机并行额度按配方条数均分，
导致"材料被平分、每条跑不满"；现在改为单配方批次内的顺序核算，不再有跨配方均摊。

## 玩家可见行为

- 产出数量 = 实际扣料对应并行 × 配方产出，不再少产或多产。
- 运行配方 A 时投入 B，B 在有空位（未到批次上限）且节流到期后独立开跑，各自进度、互不阻塞。
- 输出仓满时对应批次停在结算前，清空后自动产出。

## 验证

- `.\gradlew.bat spotlessApply build --offline` 通过；`recipeSafetyTest` 22 项断言通过。
- 实机验证要点：1000 请求产出、A/B 并行、延迟恢复、输出满等待。
- 已知取舍：批次内不再做跨配方合并（吞吐由"并行 × 多批次"承担）；如后续需跨配方合并，
  应在单配方账目稳定后作为独立特性加回。
