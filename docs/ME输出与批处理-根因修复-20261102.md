## 二、问题一：ME 输出丢失

### 2.1 当前输出机制

1. 配方完成时 `RecipeLogic.onRecipeFinish()` 负责把 `lastRecipe.outputs` 写入机器输出端。
2. 普通输出仓由 GTCEu 能力仓处理；ME 输出不是普通能力仓，而是 gtlcore 的
   `IMERecipeHandler` 链路：
   - `MEIORecipeHandlePart.meHandleOutput(...)`
   - `MEPatternBufferRecipeHandlerTraitBase.meHandleRecipeOutputInner(...)` 把产物写入机器的 `buffer`
   - `MEPatternBufferPartMachine$Ticker.tickingRequest(...)` 在网格 tick 中调用
     `AEUtils.reFunds(buffer, grid, actionSource)`，把 `buffer` 回传到 ME 网络。
3. 因此 ME 输出必须走 gtlcore 的 `RecipeRunnerHelper.handleRecipeOutput(...)`；
   它内部使用 gtlcore 的 `RecipeRunner`，会调用 ME 输出总成并把产物写入 `buffer`。

### 2.2 根因

本项目的 `onRecipeFinish()` 之前调用的是 GTCEu 原生 `handleRecipeIO(lastRecipe, IO.OUT)`。
该入口只遍历普通能力仓，不经过 gtlcore 的 `MEIORecipeHandlePart`，所以 ME 产物没有进入
`buffer`，也不会被网格 Ticker 回传 ME —— 表现为“机器进度完成，但 ME 里没有产物”。

### 2.3 修复

```java
RecipeRunnerHelper.handleRecipeOutput(getMachine(), finished);
```

同时保留结算前输出容量重检：若输出仓已满，进入 `WAITING` 并保持 `lastRecipe`/进度，
下一 tick 重试，绝不丢弃。

涉及文件：`api/machine/logic/MutableRecipesLogic.java`

## 三、问题二：批处理输入 1000、输出放大 5 倍

### 3.1 5 倍来源

默认配置：

- `ConfigHolder.batchDuration = 100`
- 零能耗机器默认 `getLimitedDuration() = 20`

批倍率上限 `= batchDuration / limitedDuration = 100 / 20 = 5`。

### 3.2 根因

旧 `findFeasibleBatch` 只用每个能力的 `getMaxParallelRatio(machine, merged, N)` 判断
“N 倍输入是否可取”。该方法对样板槽 / ME 库存输入总成等“由处理器自行决定能取多少”的
路径会高估可用量：

1. 选中 `N = 5`；
2. 实际只够 1 份输入；
3. 合并配方按 ×5 放大产出并结算；
4. 结果表现为“输入 1000、输出 5 倍”。

补充：若配方单次需要 200 份、玩家放入 1000 份，则 5 次合成产出 ×5 是正确结果。
只有在“单次需要 1000 份、却仍按 ×5 结算”时才是缺陷。

### 3.3 修复

`findFeasibleBatch` 改为对“×N 后的配方”执行与 `setupRecipe` 完全相同的模拟校验：

```java
GTRecipe scaled = merged.copy(ContentModifier.multiplier(n), false);
return RecipeRunnerHelper.matchRecipeInput(machine, scaled)
    && RecipeRunnerHelper.matchRecipeOutput(machine, scaled);
```

- N 倍输入必须能一次取齐；
- N 倍产出必须能一次放下；
- 任一不满足就折半降档，最小 1（不批处理）。

这样输入 1000 份时，N 由真实可消费量决定，输出不会超过输入所能支撑的批次数。

涉及文件：`utils/RecipeCalculationHelper.java`

## 四、问题三：多线程并发批次（后续推料不再排队）

### 4.1 当前状态（修复前）

`concurrentThreads` 只作为“机器并行 × N”的合并预算使用；执行模型是单条合并配方 + 上游状态机。
运行中后续推入的材料必须等当前配方结束才会被下一次搜索取走。

### 4.2 修复

新增 `api/machine/logic/ConcurrentBatches.java`，并在 `MutableRecipesLogic.serverTick()` 中接入：

- 同时最多推进 `concurrentThreads` 条独立批次（默认 8）；
- 每条批次独立扣料、独立进度、独立结算；
- 运行中后续推入的材料，只要还有空槽位就立刻开新批次；
- 每 tick 顺序：推进批次 → 完成批次结算（输出放不下则保留并重试）→ 补新批次 → 同步第 0 条进度给 GUI/Jade；
- `concurrentThreads = 1` 时回退上游单配方路径。

### 4.3 持久化与显示

- 批次随机器 NBT 保存；无线配方的 `wirelessEuTickInputs` 单独存 `wireless_eut`，读档重新包装为 `WirelessGTRecipe`。
- `resetRecipeLogic()` / `interruptRecipe()` 不再清空批次，避免成型回调覆盖 NBT 恢复的进度。
- Jade/GUI 的 `lastRecipe` 固定为第 0 条批次，避免把多条批次的产出合并成一份“堆叠”显示。
  若仍看到单条产出按 ×N 堆叠，那是该批次自身的并行/批处理数量，不是多批次聚合。

### 4.4 Jade 原生 Mixin 与输出显示

原生 Jade 的 `RecipeLogicProvider` 只认 `RecipeLogic.getLastRecipe()`，没有 Mixin 时并发批次信息不会出现。
已扩展 `mixin/gtceu/recipe/RecipeLogicProviderMixin`：

- `write`：写入 `gtlsupb_batches`、`gtlsupb_batch_slots` 与每条批次的 `gtlsupb_batch_progress_i`；
- `addTooltip`：显示“并发批次：n / slots”和每条批次百分比；
- 无线 EU 仍从第 0 条批次的执行配方读取；
- `lastRecipe` 改为该批次的**单份原配方**（`displayRecipe`），原生 `RecipeOutputProvider` 因此显示单份产出，
  不会把并行/批处理后的合并数量读成“堆叠数量”。

### 4.5 空转排查与修复

- 空闲全量搜索间隔由 20 tick 提高到 40 tick（2 秒）；推料/绑定变化经 `markLastRecipeDirty()` 立即清零，不延迟启动。
- 绑定样板存在但所有绑定槽位无实存材料时直接 `return emptySet()`，不再逐条 `matchRecipeInput`/并行核算；
  退化推定（`isStockedByFallback`）按“有料”处理，避免跳过共享仓机器。
- 并发批次等待原因只在变化时调用一次 `setWaiting()`，避免每 tick 重复触发 `onWaiting`。
- 已完成但输出受阻的批次不再 tick 输入，避免持续扣电。
- 日志中的 `[Preview Matcher]` 37–92ms 属结构预览；本次日志没有配方搜索耗时行，实机收益需 Spark/JFR 采样。

### 4.6 虚拟催化剂倍率

`CatalystInput.getMultiplier()` 由 `1` 改为 `0`：

- 主合成计划不再把催化剂算进需求量，也不随下单份数（1000 等）放大；
- 缺催化剂仍由 `CatalystPlanNotes` + `CraftingCalculationMixin` 以“缺少 1 个”提示；
- 独立催化剂任务仍由 `gtlsupb$beginCatalystOrder()` 以 `1L` 提交，数量恒为 1；
- 0 倍率在 LEGACY 模式由 `CraftingTreeNodeMixin` 放行；gtlcore FAST 图计算的 0 需求行为需实机确认。

### 4.7 寰宇通用厂的批处理来源

寰宇通用厂使用本项目的 `ZeroEnergyMultiTypeLogic`，不是 gtlcore 的 `BatchProcessing`。
它的 5 倍来自 `batchDuration 100 / limitedDuration 20 = 5`，由本项目 `findFeasibleBatch` 决定；
本轮已改为按真实输入/输出全量模拟降档。

## 五、问题四：配方搜索性能

### 5.1 已生效的优化（累计）

| 优化 | 作用 |
|---|---|
| 候选硬上限 8（`HARD_CANDIDATE_CAP`） | 单次搜索不再遍历全部匹配配方 |
| 执行计划缓存 40 tick | 稳态直接复用上次成功配方 |
| 空结果退避 2→4→8 tick + 20 tick 空闲节流 | 缺料/输出满时不再每 tick 全量搜索 |
| 绑定槽位数按搜索周期缓存 | 去掉 O(候选 × 部件 × 槽位) 重复遍历 |
| 样板指纹 tick+Level 记忆 | 同一 tick 多个调用点只扫描一次样板槽 |
| `markLastRecipeDirty` 清节流/计划 | 推料后立即重搜，不等待 20 tick |

### 5.2 本轮新增

1. **单候选快路径**：绑定机器稳态通常只有 1 条候选，直接跳过排序与轮转的全部临时列表分配。
2. **绑定候选直接取槽位映射**：不再每次 `getBoundRecipes()` 新建 List 再灌入 Set。
3. 批处理可行性改为全量模拟：只在批处理选择阶段执行（每次搜索一次），不进入每 tick 热路径。

### 5.3 与日志中的性能数字

日志中的 `[Preview Matcher]` 是客户端结构预览匹配耗时（37–92ms），不是配方搜索。
本次日志没有配方搜索耗时行，因此配方搜索的实机收益需要在启用细节日志后单独采样。
